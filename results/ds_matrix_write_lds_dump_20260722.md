# DS Matrix Writer Physical-Page Probe

## Question

Can `ds_write_matrix_format_f16` write a complete `32x16` FP16 fragment to
LDS when `matrix_store` is removed from the experiment?

```text
A-reg -> ds_write_matrix_format_f16 -> LDS
      -> ds_read_b128 -> global_store -> CPU bit oracle
```

## Isolation

- One wave and one 2 KiB LDS page per writer mode.
- Four writer modes: normal/trans times alt0/alt1.
- Each lane contributes eight unique finite FP16 bit patterns, 512 total.
- The full physical page is poisoned first and exported with two ordinary
  `ds_read_b128` operations per lane.
- No MLS, `ds_read_matrix`, `matrix_store`, MMAC, permutation, ABarrier, WDRA,
  or FA code is present.

## Environment

- Compiler LLVM `e0f10535...`, clang SHA256 `334cb561...`.
- PMD HEAD1694, `GPU_CHIP=sb`.
- Run: `/zys/sb/fa3b/layout_probes/ds_matrix_write_lds_dump_20260722_214911`.

## Result

`PASS`, all four modes:

```text
poison=512 unexpected=0 duplicate=0 missing=0 complete=1
complete_writers=4 total_writers=4
```

Static evidence:

```text
matrix_write=4 ds_read_b128=2 ds_write_b128=2 global_store=2
matrix_load=0 matrix_read=0 matrix_store=0 mmac=0 permute=0
SGPR14 VGPR10 private=0 sgpr_spill=0 vgpr_spill=0
```

The PMD counter reports `raw_dump_bank=96`. This is generated by the
deliberate ordinary `ds_write_b128/ds_read_b128` physical-page scan and is not
a bank-conflict measurement of the native matrix writer path.

## Interpretation

On LLVM `e0f10535` plus PMD HEAD1694, the f16 matrix writer itself transports
all 512 source values into LDS without loss for every exposed writer mode.
Therefore the existing 17-row global roundtrip failure must not be attributed
to `ds_write_matrix_format_f16`; `matrix_store_32x16_b16` or its undocumented
descriptor/source-layout contract remains the isolated blocker.

This result proves value completeness only. It does not prove that an
arbitrary MMAC output already has the writer-source layout required by dQ/dK.
That semantic contract still requires the dense MMAC oracle.
